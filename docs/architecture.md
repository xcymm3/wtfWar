# 次元竞技场当前架构

## 边界

- 浏览器负责角色库缓存、当前会话队伍选择和确定性战斗模拟；这些状态使用 `localStorage`，不保存模型密钥或持久化战报历史。
- Neon 保存全站共享角色库与模型生成指标；当前没有账号和角色归属，因此角色名称全局唯一。
- 服务端通过 `/api/characters/generate` 代理模型请求；模型只生成结构化角色数据，服务端会按同一套 schema 校验并在失败时重试。未配置模型密钥时，接口返回服务未配置，用户可改用手动创角。
- 战斗胜负由本地确定性规则引擎计算，不由模型决定；当前观战只重放会话内准备好的对局快照。

## 模块

- `types/`：角色、阶位、技能目标与团队战斗的共享领域类型；v2 会把单一 `left/right` 战斗状态扩展为有序队伍。
- `lib/schemas/`：来自 AI、导入文件和本地存储的数据校验。
- `lib/storage/`：本地存储读写与版本边界。
- `lib/battle/`：纯函数战斗引擎；`state.ts` 定义 1v1 临时状态，`realm.ts` 负责按阶位计算有效攻击、生命、固定治疗与固定护盾，`random.ts` 提供唯一允许使用的种子随机数。`battleEngine.ts` 保持既有可复现的 1v1 战斗；`teamBattleEngine.ts` 已实现 1–5 人按“红 P1→蓝 P1→红 P2→蓝 P2”交替行动、前排承伤、单体技能、群体效果、被动结算和完整队形快照，并保持 v1 回放兼容。
- `lib/balance/`：定义五个职业的合法基准角色，并用确定性种子批量模拟所有有序职业对局，输出胜率、平均回合和技能表现。
- `lib/store/gameStore.ts`：Zustand 角色库缓存与当前会话状态，负责从本地存储恢复数据、同步远端角色库，并保存双方有序队伍选择。
- `lib/characters/professionRules.ts`：职业属性范围的代码化定义；手动创角、AI 创角和数据校验必须共同使用它。
- `features/character-creator/`：手动创角表单，保存前通过 Zod 校验职业范围和技能规则。
- `lib/characters/promptCharacterGeneration.ts`：自然语言创角的请求校验和模型草稿转换；模型输出必须转换为合法角色卡。
- `features/battle-preparation/`：队伍编排组件，校验双方选择、生成可编辑种子，并在当前会话保存待观战的对战配置。
- `features/battle-observer/`：观战页只重放确定性引擎产出的结构化事件，用血量、护盾、眩晕和冷却快照驱动界面，不重新判定胜负。
- `tests/battleEngine.test.ts`：使用 Node 内置测试断言，覆盖战斗引擎的可复现性、伤害、护盾、治疗、眩晕、冷却与回合上限判定；`pnpm test` 会先运行这组测试，再验证生产构建后的主页渲染。
- `features/`：创角、角色库和战斗界面的业务模块。

## 本地数据原则

存储键为 `war-ai-game.store.v1`。本地只保存角色缓存和设置；任何本地数据在读取和写入时都必须经过 Zod 校验。旧角色迁移时默认阶位为“凡人”，并补齐技能激活方式、目标和冷却。

## 规则来源

所有角色属性、阶位、技能、站位、回合、随机性和胜负判定以 [战斗规则](./battle-rules.md) 为准。战斗规则变更时，必须同步更新引擎测试与历史战斗的 `rulesVersion` 处理策略。

## 后续实现顺序

1. 为共享角色库加入账号与角色归属。
2. 在服务端保存比赛阵容快照、结果和回放事件。
3. 建立预算约束、匹配、ELO 积分、赛季和排行榜。
4. 用批量模拟与真实比赛数据调整不同阶位、技能组合和队伍规模的平衡。
